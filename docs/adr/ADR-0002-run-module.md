# Весь контракт прогона живёт в одном модуле lib/run.py

Стадии, ETA, live-трейсинг progress.json, калибровка RTF, имена артефактов и их схемы были размазаны по `bin/transcribe` и знались в шести местах (docstring, main, Progress.finish, cmd_status, SKILL.md, README) с рассинхронизированными копиями (этапы — трижды, дефолт RTF 30.0 — дважды). Решили собрать весь контракт прогона в один глубокий модуль `lib/run.py` с двумя путями: `run()` (полный прогон) и `status()` (чтение состояния). Оболочка `bin/transcribe` сжалась с ~400 до ~90 строк и не знает ни имён файлов, ни стадий, ни формул ETA.

Рассматривались альтернативы: класс-контекст-менеджер `Run` с `read_status` (оставлял оркестрацию в main) и пара модулей `artifacts.py` + `progress.py` с sink-протоколом и watch-режимом (готовность к batch/подпискам, которых нет — отвергнут как YAGNI). Выбран вариант с двумя функциями: самый частый сценарий — один вызов `run()`, второй по частоте — один вызов `status()`.

Осознанные решения внутри: прогресс не может уронить прогон (запись best-effort), но deliverable-артефакты — строгие; финальная запись progress.json атомарна (tmp + os.replace), терминальный статус липкий; битый progress.json даёт явный `degraded`, а не молчаливый idle; `manifest.json` — commit-маркер завершённости (пишется последним). ETA-математика (`duration/20`, `rtf or 30`) — эвристика, её не улучшаем, только не дублируем дефолт.

Дополнение (2026-08-01): batch и watch остаются тонкими CLI-обёртками над
`run()`. Batch последовательно запускает один и тот же контракт для каждого
источника, а watch добавляет только polling/проверку готовности файла и
пропуск завершённых manifest; движок и внутренняя топология прогона не
изменяются.
